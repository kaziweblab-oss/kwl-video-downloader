KWL Video Downloader - Real-Time Progress Display Regression Audit
================================================================

Date: 2026-08-26
Phase: 3 - Professional UI (Human Acceptance Gate)
Reporter: Coding Agent

EXECUTIVE SUMMARY
-----------------
Fixed real-time download status display regression where progress/speed/ETA
was not displaying in the UI after multi-select changes. Two bugs identified
and fixed in apps/desktop/src/ui/App.tsx. All verification checks pass.

PROBLEM STATEMENT
-----------------
After the multi-select media cards changes, real-time download progress (percent,
speed, ETA) was not displaying during downloads. The progress display would
sometimes appear after a delay or not at all, making it appear "broken" after
the UI refactoring.

ROOT CAUSE ANALYSIS
-------------------
Two interacting architectural issues caused the regression:

1. POLLING INTERVAL CHURN (Primary)
   - Location: App.tsx:628-631
   - The `activeJobSignature` variable included an `ACTIVE_CART_STATUSES` filter:
     `filter((item) => item.jobId && ACTIVE_CART_STATUSES.includes(item.status))`
   - This signature was the dependency for a `useEffect` that sets up a 1-second
     `setInterval(pollJobs, 1000)` 
   - Every time `setCart` was called (from pollJobs), the signature recomputed
   - If the signature value changed (even from status transitions within the active
     set), the useEffect tore down the old interval and started a new one
   - During the teardown/restart window, progress updates from Rust were missed
   - After multi-select, multiple items triggered multiple setCart calls, making
     the churn frequent enough to be visibly broken

2. STALE CART ITEMS (Secondary)
   - Location: App.tsx:753
   - startCartItemJob only set `jobId: job.id` from the Rust response
   - Did NOT apply status, percent, downloadedBytes, totalBytes, speed, eta
   - Cart item stayed in pre-created state (status: 'Queued', percent: 0)
   - Progress only appeared after the next successful poll cycle
   - If that poll was disrupted by issue #1, there could be a noticeable delay

FIXES APPLIED
--------------

FIX 1: Stabilize polling interval (App.tsx:628-631)
----------------------------------------------------
Before:
  const activeJobSignature = cart
    .filter((item) => item.jobId && ACTIVE_CART_STATUSES.includes(item.status))
    .map((item) => `${item.id}:${item.jobId}`)
    .join('|');

After:
  const activeJobSignature = cart
    .filter((item) => item.jobId)
    .map((item) => `${item.id}:${item.jobId}`)
    .join('|');

Impact: Removing the ACTIVE_CART_STATUSES filter means any cart item with a
jobId triggers tracking, regardless of status. Status transitions within the
active set (Queued→Downloading→Processing→etc.) no longer destroy/recreate
the polling interval, eliminating the teardown/restart windows where progress
was missed.

FIX 2: Apply Rust response to cart item immediately (App.tsx:753-762)
-----------------------------------------------------------------------
Before:
  setCart((previous) => previous.map((entry) => (entry.id === item.id ? { ...entry, jobId: job.id } : entry)));

After:
  setCart((previous) => previous.map((entry) => (entry.id === item.id ? {
    ...entry,
    jobId: job.id,
    status: getCartItemStatus(job.status),
    percent: job.percent ?? 0,
    downloadedBytes: job.downloaded_bytes ?? 0,
    totalBytes: job.total_bytes ?? 0,
    speed: job.speed_bytes_per_second ?? 0,
    eta: job.eta_seconds ?? null,
  } : entry)));

Impact: The cart item now immediately shows the correct initial status and
progress values from the Rust response, instead of staying in a stale state
until the next poll cycle. This also provides correct display even if the
polling interval is temporarily disrupted.
